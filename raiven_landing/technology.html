🏗️ 1. System Architecture

RAVEN implements a dual-mode hybrid communication stack that dynamically switches between cloud-based delivery and peer-to-peer mesh networking based on network availability. This architecture ensures message delivery regardless of internet connectivity.

1.1 High-Level Architecture

1.3 Network Mode Selection

The Network Manager implements an automatic failover strategy:

flowchart LR A[Send Message] --> B{Internet Available?} B -->|Yes| C[Use Internet Mode] B -->|No| D{Bluetooth Enabled?} D -->|Yes| E[Use Mesh Mode] D -->|No| F[Queue for Later] C --> G[TLS → Server → Push] E --> H[BLE → Nearby Peers] F --> I[(Local Queue)] I -->|Network Returns| B
💡 Note: The mode switch is transparent to users. Messages are automatically routed via the optimal path with no manual intervention required.

💬 2. Message Lifecycle

Every message in RAVEN goes through a well-defined lifecycle from composition to delivery confirmation.

2.1 Message States

stateDiagram-v2 [*] --> COMPOSING: User types COMPOSING --> PENDING: Send pressed PENDING --> ENCRYPTING: Crypto start ENCRYPTING --> QUEUED: Encrypted QUEUED --> SENDING: Transport ready SENDING --> SENT: Left device SENT --> DELIVERED: Reached recipient DELIVERED --> READ: Opened by recipient READ --> [*] SENDING --> FAILED: Error FAILED --> QUEUED: Retry
State Symbol Description
PENDING ⏳ Message created, awaiting encryption
QUEUED 📤 Encrypted, waiting for transport
SENT ✓ Left sender's device
DELIVERED ✓✓ Reached recipient's device
READ 👁 Opened by recipient

2.2 Message Processing Pipeline

Sender Side

1. User composes message
2. Generate message ID: SHA-256(sender_id || timestamp || random_nonce)
3. Fetch recipient's public key (cached or from server)
4. Generate ephemeral X25519 keypair
5. Derive shared secret via ECDH
6. Encrypt payload with AES-256-GCM using derived key
7. Sign encrypted payload with sender's Ed25519 private key
8. Package: { id, ciphertext, nonce, signature, sender_pubkey, timestamp }
9. Route via optimal transport (Internet or Mesh)

Receiver Side

1. Receive encrypted message package
2. Verify sender signature with their public key
3. Derive shared secret from ephemeral public key
4. Decrypt payload with AES-256-GCM
5. Verify message integrity (HMAC tag in GCM)
6. Check message ID against seen-IDs cache (dedupe)
7. Store in local encrypted database
8. Send delivery acknowledgment
9. Display to user

📡 3. DTN Protocol (Offline Delivery)

RAVEN implements a custom Delay-Tolerant Networking (DTN) protocol optimized for mobile mesh networks. Based on academic research (RFC 9171) and adapted for smartphone constraints.

3.1 Store-Carry-Forward Model

sequenceDiagram participant A as Alice (Offline) participant B as Bob (Offline) participant C as Charlie (Online) participant S as Server participant D as David (Recipient) Note over A: Composes message for David A->>A: Encrypt & Queue A->>B: BLE Transfer Note over B: Stores message B->>C: BLE Transfer Note over C: Has internet! C->>S: Bridge to Server S->>D: Push Notification D->>S: Fetch Message S-->>A: Delivery ACK (when online)

3.2 Spray-and-Wait Algorithm

To limit network flooding while ensuring delivery, we implement the Binary Spray-and-Wait protocol:

flowchart TB subgraph Phase1["Phase 1: Spray"] A[Source Node] -->|L/2 copies| B[Peer 1] A -->|L/2 copies| C[Peer 2] B -->|L/4 copies| D[Peer 3] B -->|L/4 copies| E[Peer 4] end subgraph Phase2["Phase 2: Wait"] D -->|1 copy| F{Is Destination?} E -->|1 copy| F F -->|Yes| G[Deliver] F -->|No| H[Hold until contact] end
Parameter Default Value Description
L (Initial Copies) 4 Number of initial spray copies
TTL 8 hops Maximum hop count before discard
Message Expiry 72 hours Time before message is purged
Scan Interval 5 seconds BLE peer discovery frequency

3.3 Bridge Mode

When a mesh node gains internet connectivity, it acts as a Bridge:

Bridge Logic Pseudocode

func onInternetAvailable():
    for message in meshQueue:
        if message.needsBridge:
            response = server.relayMessage(message)
            if response.success:
                meshQueue.remove(message)
                broadcastAck(message.id)
⚡ Performance: In testing, 95% of mesh messages are delivered within 15 minutes in urban environments with moderate RAVEN user density.

🔄 4. Anti-Duplicate Algorithm

Mesh networks inherently create message duplicates through multi-path routing. RAVEN employs a multi-layer deduplication strategy.

4.1 Deduplication Pipeline

flowchart TD A[Incoming Message] --> B{Check Message ID} B -->|Seen| X[❌ Reject Duplicate] B -->|New| C{Check TTL} C -->|TTL = 0| X C -->|TTL > 0| D{Verify Signature} D -->|Invalid| X D -->|Valid| E{Check Timestamp} E -->|Expired| X E -->|Valid| F{Check Nonce} F -->|Replay| X F -->|Fresh| G[✅ Accept Message] G --> H[Store in Bloom Filter] G --> I[Decrement TTL] G --> J[Forward to Peers]

4.2 Bloom Filter for Seen Messages

We use a space-efficient Counting Bloom Filter to track seen message IDs:

Parameter Value Rationale
Filter Size 64 KB ~100K messages with 0.1% FP rate
Hash Functions 7 (MurmurHash3) Optimal for target FP rate
Rolling Window 24 hours Balance memory vs. coverage

4.3 Message ID Generation

ID Generation Algorithm

message_id = SHA-256(
    sender_id           // 32 bytes
    || timestamp_ms     // 8 bytes (milliseconds since epoch)
    || content_hash     // 32 bytes (SHA-256 of plaintext)
    || random_nonce     // 16 bytes (cryptographic random)
)

// Result: 32-byte unique identifier
// Collision probability: ~2^-128 (negligible)

5.3 End-to-End Encryption Flow

Encryption (Sender)

// 1. Load recipient's identity public key
recipient_pubkey = getPublicKey(recipient_id)

// 2. Generate ephemeral keypair
ephemeral_priv, ephemeral_pub = X25519.generateKeypair()

// 3. ECDH to get shared secret
shared_secret = X25519.ecdh(ephemeral_priv, recipient_pubkey)

// 4. Derive encryption key using HKDF
enc_key = HKDF(
    ikm = shared_secret,
    salt = "RAVEN-E2E-v1",
    info = sender_id || recipient_id,
    length = 32
)

// 5. Generate random nonce
nonce = randomBytes(12)

// 6. Encrypt with AES-256-GCM
ciphertext, tag = AES_GCM.encrypt(enc_key, nonce, plaintext)

// 7. Sign the package
signature = Ed25519.sign(sender_privkey, ciphertext || tag || nonce)

// 8. Package for transport
message = {
    ephemeral_pubkey,
    nonce,
    ciphertext,
    auth_tag: tag,
    signature,
    sender_id
}

5.4 Key Storage

  • iOS: Private keys stored in Secure Enclave via Keychain with kSecAttrAccessibleWhenUnlockedThisDeviceOnly
  • Android: Keys in Android Keystore with hardware-backed TEE when available
  • Database: SQLite encrypted with SQLCipher (AES-256-CBC, PBKDF2 key derivation)
⚠️ Security Note: Private keys never leave the device. They are not backed up to iCloud/Google and cannot be recovered if lost. Users should export their identity via QR pairing to a new device before resetting.

🛡️ 6. Security Model

6.1 Threat Model

Threat Mitigation
Man-in-the-Middle (MITM) Certificate pinning, X25519 ECDH, Ed25519 signatures
Replay Attacks Timestamps, nonces, message ID deduplication
Eavesdropping (Server) E2E encryption — server sees only ciphertext
Eavesdropping (Mesh) E2E encryption — relay nodes cannot decrypt
Device Theft Biometric lock, passcode, encrypted storage
Brute Force (Password) bcrypt with cost=12, rate limiting
Session Hijacking JWT with short TTL, refresh token rotation
